# Engineering Change Laboratory and Multi-Repository Intelligence (v0.5.0)

This is the operator and integrator reference for the v0.5.0 subsystems: the
repository registry, portfolios and the cross-repository graph, incremental
graph derivation and freshness, the Change Laboratory, remediation experiments,
patch export, the evidence ledger, and the operator control plane.

Everything below describes behaviour that exists in the code on this branch.
Where a guarantee is asserted by policy rather than enforced by the operating
system, it says so.

## Autonomy boundary

```text
Project Brain may apply candidate patches only inside disposable managed workspaces for validation. It does not apply patches to authoritative repositories, commit changes, push branches, merge pull requests, or deploy software.
```

The autonomy classification remains **L1**. v0.5.0 adds no capability that
writes to an authoritative repository. Concretely, no code path in `brain/lab`,
`brain/experiments`, or `brain/control` commits, pushes, opens or merges a pull
request, deploys, or edits a registered repository's working tree. The only
writes into a registered repository's directory are Brain's own metadata under
`<repo>/.brain/` (graph generations), and `git worktree add`/`remove` of a
detached worktree inside the managed workspace root.

The end of the lifecycle is an **exported patch**: a unified diff plus
application instructions, written to a directory a human chooses. Applying it
is a human action.

## 1. Repository registration

A repository must be registered before any other subsystem will touch it. The
registry is the only place a filesystem path enters the system; every other
CLI and endpoint takes a `repository_id` and resolves the root itself. Callers
never supply paths to the laboratory or the experiment runner.

```bash
py -3 -m brain.workspace.cli repositories register --path /path/to/repo --name my-service --trust trusted_internal
```

Registration resolves the canonical root, derives a stable `repository_id` from
it, reads the current Git revision and default branch, detects languages, and
assigns the default capability set for the trust level. Path admission
(`brain/workspace/path_sandbox.py`) rejects: a root outside the allowed roots,
a root that is not a Git checkout (except for the `fixture` trust level), the
home directory itself unless `--allow-home` is passed, and a path that
normalizes onto an already-registered repository (the duplicate-registration
case). Registration is versioned and optimistically locked; concurrent writers
get `OptimisticLockError` rather than a lost update.

Every registry mutation appends an audit event (`repositories events`), and
`repositories verify` re-checks stored integrity.

Storage: `.brain/workspace/` relative to the working directory.

## 2. Trust levels

| Trust level | Meaning |
| --- | --- |
| `trusted_internal` | A repository the operator owns. Full v0.5.0 capability set. |
| `trusted_read_only` | Analysis only: read, history, graph. No workspace, no patch, no validation. |
| `untrusted_external` | Source may be read. Nothing else. |
| `fixture` | Test and demonstration repositories. Workspace and validation, but no patch export. |
| `disabled` | No capabilities. |

Trust is resolved server-side. The API never accepts a trusted role from a
request body beyond the declared `trust_level` string, which is validated
against the enum and then used only to look up defaults.

## 3. Capabilities

Capabilities are the actual permission check; trust level only chooses the
defaults. Every guarded operation names the capability it needs and fails
closed when it is absent.

`read_source`, `read_git_history`, `build_graph`, `write_brain_metadata`,
`create_worktrees`, `apply_candidate_patches`, `execute_validation`,
`export_patch`, `update_baseline`, `mutate_policy`, `mutate_waivers`.

Defaults:

| Trust level | Capabilities |
| --- | --- |
| `trusted_internal` | read_source, read_git_history, build_graph, write_brain_metadata, create_worktrees, apply_candidate_patches, execute_validation, export_patch, update_baseline |
| `trusted_read_only` | read_source, read_git_history, build_graph |
| `untrusted_external` | read_source |
| `fixture` | read_source, read_git_history, build_graph, create_worktrees, apply_candidate_patches, execute_validation |
| `disabled` | *(none)* |

`mutate_policy` and `mutate_waivers` are never granted by default at any trust
level. Nothing in v0.5.0 grants itself a capability.

## 4. Portfolio configuration

A portfolio is a named set of registered repositories plus the contracts
between them. Configuration is a YAML document:

```yaml
version: 1
portfolio:
  name: orders-platform
  owners: [platform-team]
  architecture_policy: clients call APIs; only services import contracts
repositories:
  shared-contracts: { repository_id: repo-…, role: library }
  api-service:      { repository_id: repo-…, role: service }
  worker-service:   { repository_id: repo-…, role: service }
  web-client:       { repository_id: repo-…, role: client }
  deployment-config:{ repository_id: repo-…, role: configuration }
contracts:
  - { from: api-service,  to: shared-contracts, type: depends_on_package, allowed: true }
  - { from: worker-service, to: shared-contracts, type: consumes_event,   allowed: true }
  - { from: web-client,   to: api-service,      type: calls_api,          allowed: true }
  - { from: web-client,   to: worker-service,   type: depends_on_package, allowed: false }
```

```bash
py -3 -m brain.portfolio.cli create --config portfolio.yaml
py -3 -m brain.portfolio.cli build <portfolio-id>
```

Parsing rejects an unsupported schema version, duplicate aliases, a contract
referencing an unknown alias, a self-referencing contract, and two contracts
that contradict each other on the same `(from, to, type)`.

`build` reads each repository's revision and graph-generation status **from the
registry**. A portfolio whose repositories are not all registered fails: the
CLI exits non-zero and the API returns `409`. A generation records the revision
it was built from, so an unresolvable placeholder is never stored as current.

Storage: `.brain/portfolio/`.

## 5. Cross-repository contracts and the portfolio graph

The portfolio graph derives relationships from the repositories themselves and
compares them against the declared contracts. It reports:

- **Undocumented dependency** — an observed relationship with no contract.
- **Forbidden dependency** — an observed relationship whose contract says
  `allowed: false` (for example a client importing worker source directly
  instead of calling the API).
- **Circular dependency** — a cycle across repository boundaries.
- **Coupling metrics** — per-repository fan-in/fan-out and the portfolio-level
  aggregate (`portfolio.cli coupling`).

A generation is activated only when its quality report passes; a failing
generation is stored but the previously active generation stays active. That
is the graph-activation rollback path.

## 6. Incremental intelligence

`brain/freshness/incremental_planner.py` plans an update between two
revisions from the real Git diff: added, modified, deleted and renamed files,
the affected symbols and relationships, the dependent entities, and the
resulting stale node and relationship sets.

```bash
py -3 -m brain.freshness.cli plan    --repository <id> --base <rev> --candidate <rev>
py -3 -m brain.freshness.cli rebuild --repository <id> [--full] [--no-activate]
```

The planner emits a `decision` of `incremental` or `full_rebuild`. It falls
back to a full rebuild, recording a `fallback_reason`, when there is no base
generation to derive from, when the diff cannot be resolved, when the change
set is too broad to be worth deriving, or when the operator passes `--full`.
An interrupted build leaves the previous generation active; the interrupted
generation is not activated.

`rebuild` is an explicit operator action. A status query never triggers one.

## 7. Freshness

Every derived artifact carries a freshness state: `current`, `stale`,
`building`, `failed`, `unknown`, `superseded`. Artifact types include
repository registration, source revision, repository graph, portfolio graph,
baseline, trend, impact analysis, remediation plan, patch proposal, and
experiment result.

```bash
py -3 -m brain.freshness.cli status  --repository <id>
py -3 -m brain.freshness.cli explain --artifact graph:<repository-id>
```

`status` compares the active generation's revision against the revision
observed in the checkout right now; they diverge exactly when the graph is
stale. `explain` returns why one artifact is in its current state, and exits
non-zero for an unknown artifact rather than reporting a confident "current".

Storage: `.brain/freshness/`; per-repository generations live in
`<repo>/.brain/`.

## 8. Caches

Graph generations are content-addressed per revision and kept under the
repository's own `.brain/` directory, with an explicit active-generation
pointer. Derivation reuses the active generation as the base; there is no
opaque global cache that can outlive an invalidation. Cache invalidation is the
freshness record: an artifact marked `stale` is not served as `current`.

## 9. Change Laboratory: workspace security

The laboratory is the only component that applies a candidate patch, and it
applies it only inside a disposable managed workspace.

Workspace creation prefers `git worktree add --detach <ws> <base-revision>` and
falls back to a filtered copy when the source is not a Git checkout or the
worktree is refused; the record stores which method was used and, for the
fallback, why. The copy ignores `.git`, `.brain`, `__pycache__`, `.venv`,
`venv`, `node_modules`, `.mypy_cache`.

Security properties that are enforced in code:

- Every workspace directory lives under the managed root and carries an
  ownership marker naming its `workspace_id`. Nothing is deleted unless the
  path resolves inside the managed root *and* the marker matches the expected
  record.
- Path resolution rejects traversal, absolute paths, and symlink escapes.
- Validation processes are launched with an argv list — never a shell string,
  never `shell=True`.
- Executables are resolved from an allowlist (`python`, `python3`, `py`,
  `pytest`, `mypy`, `ruff`); a repository-provided path is refused.
- The child environment is built from an allowlist (`PATH`, `PATHEXT`,
  `SYSTEMROOT`, `WINDIR`, `COMSPEC`, `TEMP`, `TMP`, `TMPDIR`, `LANG`, `LC_ALL`,
  and the `PYTHON*` determinism variables). Process secrets are not inherited,
  and a profile that declares a secret-like variable is rejected.
- Output is truncated per stream, and a process tree that outlives its timeout
  is killed and reported.

**Network isolation is `unverified`.** `BRAIN_LAB_NETWORK_POLICY=deny` is set
in the child environment and the constraint is asserted by policy, but no
OS-level network namespace, firewall rule, or sandbox is applied. Every
validation report carries `network_isolation: "unverified"`. Do not read this
as a sandbox.

Workspace states: `requested`, `preparing`, `ready`, `patching`, `validating`,
`passed`, `failed`, `cancelled`, `expired`, `cleaning`, `cleaned`,
`quarantined`.

### Deployment restriction: local trusted host only

Because network isolation is unverified, the laboratory — meaning anything
that executes validation commands — is approved for **a local trusted host
only**. The read-only side of v0.5.0 (registry inspection, repository and
portfolio graphs, freshness, impact, the control-plane summary) carries no
such restriction and may run on staging.

Until OS-level isolation is applied and evidenced, an execution-capable
deployment must not be given:

- untrusted or externally contributed repositories;
- production credentials of any kind;
- caller-supplied validation profiles outside the built-in allowlist;
- sensitive private repositories sharing a host with third-party code.

This is a deployment boundary, not a code guarantee. Raising it requires
evidence of a network namespace, firewall rule, or sandbox — not a policy
statement. See §11 and the known limitations.

## 10. Validation profiles

A profile is a named, allowlisted command sequence. Two are built in:

| Profile | Timeout | Commands |
| --- | --- | --- |
| `python-compile` | 300 s | `python -m compileall -q .` (required) |
| `python-standard` | 900 s | `python -m compileall -q .`, `python -m pytest -q` (both required) |

Additional profiles may be dropped into `.brain/lab/profiles/*.json`. A profile
is rejected when it declares more than 20 commands, a timeout above 3600 s, an
executable outside the allowlist, an executable given as a path, or a
secret-like environment variable.

A repository additionally carries `allowed_validation_profiles`. The laboratory
refuses any profile outside that list, so a repository can be registered such
that only compilation — never a test run — may execute against it.

```bash
py -3 -m brain.lab.cli profiles
py -3 -m brain.lab.cli validate --repository <id> --patch-file fix.diff --profile python-compile
```

## 11. Candidate patch limitations

Patches are unified diffs, checked before they go near a workspace
(`PatchValidator`). Rejected: empty content, NUL bytes, more than
`max_bytes` (default 500 000), more than `max_files` distinct targets (default
50), a symlink mode change (`120000`), an absolute target path, `..` traversal,
any target under `.git/`, the workspace ownership marker, a target outside the
declared `--allow-path` scope, and a patch whose recorded base file hashes no
longer match the tree (the stale-patch case).

Application uses `git apply` with a pre-check. **Zero-context hunks are not
accepted**: `--unidiff-zero` is deliberately not passed, so a generated patch
must carry real context lines. Application is snapshot-backed up to 20 MiB and
rolls back on failure; the result records affected files with before and after
hashes.

Patches are applied to the workspace copy only. The authoritative checkout is
never modified — the fixture-portfolio scenarios and the CLI and API contract
suites assert `git status --porcelain` is empty after every patch path.

## 12. Experiment lifecycle

An experiment compares two or more candidate patches for the same finding.

```bash
py -3 -m brain.experiments.cli create --repository <id> --option a.diff --option b.diff --profile python-compile
py -3 -m brain.experiments.cli run <experiment-id>
py -3 -m brain.experiments.cli compare <experiment-id>
py -3 -m brain.experiments.cli recommend <experiment-id>
```

States: `proposed`, `queued`, `preparing`, `running`, `comparing`,
`completed`, `failed`, `cancelled`, `stale`, `superseded`.

Each option gets its own disposable workspace, its own patch application, and
its own validation run. Workspaces are cleaned when the experiment finishes
unless `--retain-workspaces` is passed. `cancel` sets the cancellation event;
a run in progress stops at the next checkpoint and is reported as cancelled,
not failed.

An experiment whose repository moved to a new revision after creation is marked
**stale** and its conclusion is not treated as current evidence.

Conclusions: `recommend_option`, `multiple_equivalent`, `no_safe_option`,
`insufficient_evidence`, `all_failed`, `experiment_stale`.

## 13. Comparison formula

Comparison is deterministic and arithmetic. **No language model participates.**

Each option's metrics are min-max normalized within the surviving option set
and combined by a fixed weighting that sums to 100:

| Dimension | Weight | Direction |
| --- | ---: | --- |
| `findings_net` (resolved − new) | 25 | higher is better |
| `coupling_delta` | 12 | lower is better |
| `optional_tests` passed | 10 | higher is better |
| `blast_radius` | 10 | lower is better |
| `cycle_delta` | 8 | lower is better |
| `hotspot_delta` | 8 | lower is better |
| `forbidden_edge_delta` | 7 | lower is better |
| `changed_files` | 5 | lower is better |
| `changed_lines` | 5 | lower is better |
| `rollback_complexity` | 5 | lower is better |
| `validation_duration` | 3 | lower is better |
| `unresolved_uncertainty` | 2 | lower is better |

Disqualification happens before ranking, and a disqualified option cannot be
recommended regardless of score. An option is disqualified when it was never
executed, when it failed a required validation command, when it introduced a
new critical architecture violation or a new forbidden edge (unless the
experiment's `policy_allows_new_critical` says otherwise), or when it added new
findings without improving the architecture. New critical violations and new
forbidden edges are reported as prominent warnings whether or not policy
tolerates them — a suppressed violation nobody sees is the failure mode.

Two options within `TIE_EPSILON` (0.01) are
reported as a tie (`multiple_equivalent`) rather than being separated by
iteration order. The formula string is stored on every comparison, so a
recommendation can be re-derived from the recorded metrics.

## 14. Patch export

Export is the terminal step and the human hand-off.

```bash
py -3 -m brain.experiments.cli action <experiment-id> --action accept_for_export --option-id opt-2 --actor alice
py -3 -m brain.experiments.cli export <experiment-id> --option-id opt-2 --out ./patches
```

Rules enforced in code:

- Export requires a recorded human `accept_for_export` action naming that
  option. Brain does not approve its own remediation plan; `recommend` reports
  `approval_status: "not_approved"`.
- Export fails with `ExportStaleError` when the authoritative revision has moved
  since the experiment's base revision, unless the operator explicitly passes
  `--revalidated`.
- The export writes `<export-id>.diff` and `<export-id>.json` into the chosen
  directory and returns `applied_to_repository: false`. It contains the unified
  diff, the expected source hashes, the validation summary, and application
  instructions for a human.

Human workflow actions: `acknowledge`, `accept_for_export`, `reject`,
`request_another`, `mark_applied`, `verify_external`. `mark_applied` records
that a human applied the patch; it does not apply anything.

## 15. Evidence ledger

An append-only, hash-chained record of what happened.

```bash
py -3 -m brain.ledger.cli health
py -3 -m brain.ledger.cli verify
py -3 -m brain.ledger.cli export --output ledger.jsonl
py -3 -m brain.ledger.cli verify --input ledger.jsonl
```

Each event stores the previous event's hash, so modification, deletion, and
reordering are all detectable — verification reports the sequence and the
failing code rather than a bare boolean. SQLite `BEFORE UPDATE` and
`BEFORE DELETE` triggers refuse in-place edits at the storage layer.

There is **no generic writer**. Events are appended only through named product
recorders (repository registered, capability changed, graph generation built
and activated, graph build failed, portfolio generation activated, finding
created, remediation plan proposed and decided, workspace created, workspace
state changed, patch applied in workspace, validation command executed,
experiment completed, recommendation acknowledged, patch exported, human marked
patch applied, verification, artifact superseded, redaction). There is no
delete path and no ledger write endpoint over HTTP; a redaction is itself an
appended event.

Storage: `.brain/ledger/ledger.sqlite3`.

## 16. Operator control plane and action queue

```bash
py -3 -m brain.control.cli summary
py -3 -m brain.control.cli queue --max-priority 2
py -3 -m brain.control.cli metrics
py -3 -m brain.control.cli health
```

The control plane is **read-only**. It reports registry state, freshness, graph
generations, active and quarantined workspaces, experiments, ledger health, and
budget usage. Every control-plane endpoint is a `GET`; none performs the action
it surfaces.

The action queue lists what needs a human decision, drawn from a fixed set:
`approve_remediation_plan`, `clean_quarantined_workspace`,
`inspect_failed_experiment`, `investigate_graph_build_failure`,
`resolve_expired_waiver`, `revalidate_stale_patch`, `review_high_risk_change`,
`verify_manually_applied_patch`. There is no universal admin endpoint.

## 20. Cleanup, recovery, and quarantine

```bash
py -3 -m brain.lab.cli clean --workspace <workspace-id> --reason "done"
py -3 -m brain.lab.cli recover
```

`clean` removes a workspace only after verifying the path resolves inside the
managed root and the ownership marker matches the expected record. A Git
worktree is removed with `git worktree remove --force` so the source repository
does not keep a dangling registration.

When disposal is not provably safe — a locked file, a permission error, a
marker that does not match — the workspace is **quarantined** rather than
force-deleted: its state becomes `quarantined`, the reason is recorded, and the
control plane raises a `clean_quarantined_workspace` action for a human. A
quarantined workspace is never silently reused or removed.

`recover` expires workspaces past their deadline and reconciles the managed
root with the record store. A directory with no record is removed **only** when
it carries a valid ownership marker naming itself; anything else is reported
and left untouched. A record whose directory has vanished is marked cleaned
with `cleanup_status: "vanished"`. Orphaned validation processes are killed by
process tree at timeout and at cleanup.

## Known limitations

1. **Network isolation is unverified.** Asserted by environment policy only; no
   OS-level enforcement. Treat validation as running with the host's network
   access. Consequently execution is approved for a local trusted host only —
   see §9, "Deployment restriction".
2. **No filesystem sandbox beyond path checks.** A validation command runs as
   the same OS user with the same filesystem permissions. The allowlist of
   executables and the argv-only launch are the containment, not a jail.
3. **Zero-context patches are rejected.** Any generator feeding the laboratory
   must emit diffs with context lines.
4. **Relationship derivation is language-scoped.** Cross-repository detection is
   strongest for Python source, package requirements, event topics, and
   declarative deployment topology. Other ecosystems will under-report.
5. **The evidence ledger is written by the orchestrating layer**, not by every
   subsystem automatically. A subsystem invoked directly through its own CLI
   does not itself append an event.
6. **Budgets observe local state only.** They bound this installation; they say
   nothing about a second process on another host sharing the same repository.
7. **Comparison depends on the metrics the analysis produced.** Where an
   analyzer cannot measure a dimension it contributes zero, which the
   comparison reports as `unresolved_uncertainty` rather than hiding.
8. **Export does not verify the patch still applies** to a moved authoritative
   revision; it refuses to export instead, and requires explicit
   `--revalidated` to override.
