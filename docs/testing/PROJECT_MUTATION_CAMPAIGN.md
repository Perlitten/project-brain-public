# Whole-package mutation campaign

This campaign starts from `e93e8a32e032a546172c7dfb0241a9e60b0b81b2` and includes
the team features merged in #99. The target is at least 70% overall and 80% in
each security-sensitive module. **Generation and successful ordinary tests do
not establish either target.** Results remain incomplete until every shard is
accounted for and survivors have been reviewed.

The focused behavior/test patch is reviewed in
[PR #109](https://github.com/Perlitten/project-brain-public/pull/109).
The process-supervision test correction is reviewed separately in
[PR #110](https://github.com/Perlitten/project-brain-public/pull/110).
PR #108 carries the campaign tooling and evidence and retains both patches for
combined validation. The behavior branch independently passes 2,545 tests;
the laboratory branch independently passes 2,542. The infrastructure PR remains
a draft pending the full-package campaign.

## Frozen scope and scoring

The [inventory](evidence/project-mutation-inventory.json) records source hashes,
generated-body hashes, candidate identity hashes and counts for every tracked Python module under
`brain`, `apps` and `scripts`: **434 modules, 107,501 candidates** generated by
`mutmut==3.8.0`. There are no explicit module exclusions, coverage-only filters,
call-depth cutoffs or `pragma no mutate` additions. CLI implementations remain
included because they contain configuration and validation behavior. Scripts
are included conservatively, including historical release tooling.

The inventory contains 80 modules with zero generated candidates. These remain
listed, with an undefined score rather than an invented 100%. Mutmut's operators
primarily transform function bodies; module-level declarations, schema fields
and annotations are a tool limitation. Their absence from the generated universe
must not be presented as mutation coverage of those declarations.

The reporting formula is:

`killed / (total - equivalent - type_invalid)`

Timeouts remain in the denominator. Missing-test candidates remain undetected
and are also shown separately as `no_tests` (a subset of `survived`). Pytest
internal errors, crashes, interrupted executions and unreviewed type-check
results are inconclusive, not kills. An incomplete run has no final score.
Equivalent/type-invalid exclusions require individual justification. The
[compressed compiler proof](evidence/project-mutation-type-proof.json.gz) binds
**35,131 type-invalid candidates** to mypy diagnostics and generated-body hashes;
**72,370 candidates** remain before equivalence review. No equivalent candidates
are automatically excluded.

Mypy's duplicate-attribute diagnostics caused by cloning constructor methods are
retained separately after checking matching attribute annotations. They do not
qualify a candidate for exclusion. Other errors outside individual mutant spans
block automatic type exclusions for that module. The production mypy gate and
its zero-error baseline are unchanged. Static proof is limited by existing
annotations and mypy's handling of untyped code.

## Execution isolation

The optional `mutation-baseline` PR label starts 32 deterministic module shards
on standard public GitHub runners, capped at 16 concurrent jobs. Every shard
gets separate PostgreSQL, Redis and Neo4j services and executes one mutant at a
time. This prevents concurrent fixtures from dropping each other's tables or
corrupting shared cache state. Sharding preserves the complete inventory.

The mutation-only Python startup guard blocks non-loopback socket connections,
removes provider keys and sets Hugging Face/Transformers offline flags. Tests
use mock providers and local fixtures. Dependency/container preparation precedes
verification; there are no model downloads or remote inference requests.
Normal application behavior and the existing CI/benchmark gates are unchanged.
This Python guard is not an OS-wide firewall for arbitrary native subprocesses.

Before measuring, mutmut runs unmutated instrumented tests and a forced-failure
sentinel. A pytest plugin additionally rejects production imports from another
checkout. CLI subprocesses retain the campaign configuration across working
directory/PYTHONPATH changes; their function hits are associated with the parent
test. Named mutants also execute when Python runs their module as `__main__`.
A temporary, conditional venv startup hook is removed after measurement and
does not alter ordinary provider processes.

A shard with no function/test associations can only record candidates
as uncovered after a completed, passing clean suite. It does not exclude them.
Processes deliberately clearing the campaign environment or using isolated
Python startup remain a coverage limitation; their effects must be investigated
before treating an unassociated candidate as equivalent.

Raw metadata, source/test fingerprints, elapsed time and failed-test witnesses
are retained per shard. Witnesses contain test identifiers and exception types,
without traceback locals or credentials. GitHub artifacts have one-day retention
and must be collected into the final evidence before expiry. Exact-head caches
allow interrupted runs to resume without reusing results across test changes.

## Reproduce

Use Linux x86_64 and Python 3.12 for the fork-based mutation engine, in a dedicated
tool environment outside any running application's venv:

```bash
python -m venv /tmp/brain-mutation-tools
source /tmp/brain-mutation-tools/bin/activate
python -m pip install --require-hashes -r requirements-dev.lock -r eval/mutation-requirements.lock
python -m pip install --no-deps -e .
python -m eval.project_mutation generate --workers 4 \
  --output generated-inventory.json
(
  cd mutants
  python -m mypy --explicit-package-bases --follow-imports=silent --output=json brain apps scripts \
    > ../mutant-type-diagnostics.jsonl || test "$?" -eq 1
)
python -m eval.project_mutation types \
  --inventory generated-inventory.json --diagnostics mutant-type-diagnostics.jsonl \
  --output generated-type-proof.json.gz
python -m eval.project_mutation plan \
  --inventory docs/testing/evidence/project-mutation-inventory.json \
  --shards 32 --output mutation-plan.json
```

Generation requires a fresh `mutants` directory; preserve any earlier results
outside the checkout first. Compare the generated counts and candidate hashes
with the committed inventory before replaying the frozen campaign.

Provide disposable local PostgreSQL/Redis/Neo4j fixtures using the existing CI
environment variables, PostgreSQL recovery clients on PATH, and the opted-in
`TEST_TEAM_POSTGRES_URL`. That database must be named `brain_team_test`, owned
by the non-superuser `fixture` with CREATEDB. Never point the suite at operator
data. On a shared cloud host the guard blocks the usual operator ports; use
separate fixture ports. In a disposable CI runner the workflow explicitly allows
its own service ports.

Run each shard from a separate checkout/sandbox with its own fixtures:

```bash
mkdir -p .mutation-results/witnesses
export PYTHONPATH="$PWD/eval/mutation_support"
export PYTEST_PLUGINS=import_check
export BRAIN_MUTATION_WITNESSES="$PWD/.mutation-results/witnesses"
python -m eval.project_mutation run \
  --inventory docs/testing/evidence/project-mutation-inventory.json \
  --type-proof docs/testing/evidence/project-mutation-type-proof.json.gz \
  --shards 32 --shard 0 --output .mutation-results/report.json
```

Repeat indices 0–31. Do not run shards concurrently in the same checkout or
against the same databases. Do not interpret a completed subset as the overall
score. Changed production bytes require a newly generated inventory, retaining
the old one for the before/after comparison.

## Assemble shard evidence

Download and unpack all `mutation-shard-N` artifacts before their one-day expiry,
keeping each `report.json` in its own shard directory. Recompute rather than
average their scores:

```bash
python -m eval.project_mutation_aggregate artifacts/*/.mutation-results/report.json \
  --inventory docs/testing/evidence/project-mutation-inventory.json \
  --type-proof docs/testing/evidence/project-mutation-type-proof.json.gz \
  --output project-mutation-baseline.json
```

The aggregator rejects duplicate shards, different tests/compiler proof/source
fingerprints and changed candidate identities. Missing shards and failed runner
controls have no overall score. It recomputes every count from raw exit codes,
keeps timeouts in the denominator and lists all unclassified survivors. An
optional `--classifications decisions.json` maps candidate keys to a classification
(`real_gap`, `equivalent`, `untestable`), a reason and the original `source_sha256`.
Only individually justified equivalences are excluded; untestable candidates
stay in the denominator. A complete raw score alone does not satisfy acceptance:
every survivor still needs review, and every security-sensitive module needs
its separate threshold check.

The unchanged production mypy gate remains **0 errors across 434 files**. The

## Cache and assertion hardening

A local OAuth attempt was discarded because an incremental statistics cache
collected only two unrelated new tests after the selected module changed. Its
zero-association result is not a baseline and is never included in a score.
Every run now recollects full statistics. Selected files are regenerated once
because raw files copied for another scope can otherwise have mtimes that
mutmut mistakes for generated code. A real two-module regression exercises
that failure. A context envelope also binds resumable outcomes to production,
test, runner and dependency fingerprints; changed assertions cannot retain old
kills. The integration test verifies both fresh scope association and rejection
of a stale kill after a synthetic test contract changes.

Two repository-self-scan drift cases that accepted readiness fallbacks or empty
list equality are replaced by one controlled repository case. It requires two
distinct drift findings, correct severity/source evidence, repeatable identifiers
and unchanged identifiers when source lines move. A version-floor placeholder
is removed; release identity has dedicated existing contract tests.

Three persisted OAuth cases add client-update isolation, token attribution,
paired rotation/revocation, absence of raw tokens on disk, unaffected other
clients, SQLite timezone handling and exact independent access/refresh deadlines.
The existing PostgreSQL overlap case now holds a public database row lock and
waits for both real HTTP transactions to contend. It no longer patches a private
OAuth helper or relies on an arbitrary scheduling delay. The same existing
issued-token case now verifies the principal's service kind.
